# 工业软件平台多模式协同智能问答系统・项目报告

> 用途：个人简历项目经历支撑材料 + 秋招面试准备底稿
> 项目性质：独立设计开发的完整全栈项目（个人项目，无团队分工背景）
> 面试定位：大模型应用开发 / AI 应用 / 后端开发方向主项目



***

## 一、项目背景与目标

工业软件平台的生态运营（众包、众创、众扶等多模式协同场景）中，积累了大量的非结构化文档资料 —— 包括平台运营手册、技术方案、案例文档、行业知识材料等。这些知识分散在不同文档里，缺乏统一组织与检索手段，业务人员与平台用户难以快速、准确地获取所需知识，导致知识利用率低、问答依赖人工经验。

本项目目标是构建一套面向工业垂直领域的**多模式协同智能问答系统**：以 "BM25 关键词检索 + 向量语义检索 + 知识图谱检索" 三条检索通道混合召回、加权融合的方式，让系统既能在关键词层面精确命中，又能在语义层面理解用户意图，还能利用实体关系网络回答 "谁与谁相关、某事关联哪些环节" 等关系型问题，最终由千问大模型基于检索证据生成可信、可溯源的回答。同时提供完整的用户体系（注册、登录、登出、修改密码）、文档管理（上传、处理状态跟踪、删除、失败重试）与知识图谱可视化能力，形成可落地的工业知识服务闭环。

## 二、系统总体架构

系统采用前后端分离的分层架构，整体由四层组成：

**前端展示层**：基于 Vue3 + Vite + Element Plus + Pinia + ECharts 构建的单页应用，包含智能问答、文档管理、知识图谱可视化、个人中心四大模块，通过 Vite 开发代理将 `/api` 请求转发至后端。

**RESTful API 服务层**：基于 FastAPI 实现，按业务域划分为认证（auth）、文档（documents）、会话问答（chats）、图谱与检索（search）四组路由，共 16 个接口；统一 JWT 鉴权依赖注入、统一异常处理与响应结构。

**业务服务层**：核心引擎所在。包括文档解析与分块、向量化服务（千问 embedding）、BM25 检索、向量检索（Chroma）、知识图谱构建与检索（Neo4j + 千问 LLM 实体抽取）、RRF 融合检索、RAG 问答编排、缓存与认证安全等模块，模块间通过明确的依赖关系解耦。

**数据存储层**：按职责分离原则划分为四个存储 ——MySQL 承载业务持久化（用户、文档、文档分块、会话、聊天消息五张表）；Redis 承载 JWT 登出黑名单与热点问答缓存；Chroma 向量数据库承载文档分块的高维向量（余弦相似度检索）；Neo4j 图数据库承载工业领域知识图谱（Document / Chunk / Entity 三类节点，PART\_OF / MENTIONED / RELATED 三类关系）。

大模型与嵌入模型均采用通义千问（LLM 为 qwen-plus，嵌入为 text-embedding-v3，1024 维），通过 OpenAI SDK 兼容端点调用，模型名、BaseURL、API Key 全部在 `.env` 中配置，支持按环境切换。

## 三、核心功能模块

### 3.1 用户认证与安全体系

实现注册、登录、登出、修改密码完整闭环。登录签发 JWT（含 jti 与 token\_version），密码经 bcrypt 加盐哈希存储；登出时将 token 的 jti 写入 Redis 黑名单，其 TTL 与 token 剩余有效期一致，实现 "登出即失效"；修改密码时通过自增 token\_version 使该用户所有历史 token 立即失效，从根本上防止旧凭证复用。全链路实测通过：错密码 401、登出后旧 token 401、改密后旧 token 401。

### 3.2 文档处理流水线（本项目重点之一）

上传的文档进入一条带状态机的后台异步流水线：`uploaded → parsing（解析）→ vectorizing（向量化）→ kg_building（图谱构建）→ ready（就绪）/ failed（失败）`。任何环节失败都记录错误信息并允许一键重试，重试前自动清理该文档的残留数据（向量、图谱、分块），避免脏数据累积。上传接口同时具备扩展名白名单、50MB 大小上限与同名文件查重校验（重复上传返回 409）。

### 3.3 三路混合检索（本项目重点之二）

**BM25 关键词检索**：对文档分块做 jieba 中文分词，构建倒排索引与 BM25 打分，精确匹配关键词类查询，响应在毫秒级。

**向量语义检索**：文档分块经千问 text-embedding-v3 嵌入为 1024 维向量写入 Chroma，查询时对问题向量做余弦相似度检索，召回语义相近但无关键词重叠的内容。

**知识图谱检索**：从文档分块中利用千问 LLM 抽取工业领域实体（设备、故障、模式、技术方案等）与实体间关系，构建 Neo4j 图谱；检索时将问题做实体链接与 jieba 匹配，命中实体后沿关系做一跳邻居扩展，再回溯到这些实体的证据分块，从而回答关系型问题。

**RRF 加权融合**：三路结果按倒数排名融合（RRF）算法合并，三路各自的权重、每路 TOP\_K、RRF 常数 K 均在 `.env` 中可配置；任一路检索失败自动降级，不阻塞整体问答。实测三路各召回 10 条、融合后取 6 条送入大模型，千问基于证据生成带来源的答案。

### 3.4 RAG 问答编排

用户问题经三路检索召回证据片段后，与系统提示词、对话历史一起组装为上下文，调用千问 qwen-plus 生成回答并附带检索统计（各检索路命中数、是否缓存命中）。热点问答结果写入 Redis 缓存，命中缓存的重复问题直接返回，降低大模型调用成本与响应延迟。

### 3.5 知识图谱可视化

前端基于 ECharts 力导向图渲染图谱，后端提供图谱子图接口（节点、关系、类型），实体与文档分色展示，支持缩放与节点数量控制。

## 四、关键技术难点与解决方案

**难点一：千问 embedding 接口的批量上限限制。** 初版将文档全部分块一次性提交给 embedding 接口，触发 `400 batch size is invalid` 错误，大文档处理必然失败。解决方案：阅读接口文档确认单次批量上限为 20 条后，改造为按 20 条 / 批分批 upsert 到 Chroma，实测 1100 块文档全量向量化成功。

**难点二：大文档知识图谱构建耗时不可接受。** 初版对每个分块逐个调用大模型抽取实体（约 8 秒 / 块），1103 块的中等文档预计耗时 2.5 小时以上，且全部抽完才一次性写入 Neo4j，导致处理期间图谱永远空白、体验上表现为 "卡死"。解决方案分三步：一是将分块按约 4000 字符合并为窗口，一次 LLM 调用抽取一个窗口内的实体与关系，调用次数从 "分块数" 降为 "窗口数"（约 1/20）；二是引入 3 路并发线程池并行处理窗口；三是改为 "每窗口抽完立即增量写入 Neo4j"（MERGE 幂等，同名实体自动合并），处理进度实时可见。优化后 74KB/1100 块文档全流程（向量化 + 图谱构建）从小时级降至 **150 秒**。

**难点三：服务重启导致文档处理永久卡死。** 后台线程处理中服务重启，文档状态永远停留在中间态（parsing/vectorizing/kg\_building），无法继续也无法重试。解决方案：在 FastAPI lifespan 启动钩子中自动扫描并把这些残留中间态文档重置为 failed 并附说明，用户一键重试即可用优化后的流水线重新处理，杜绝永久卡死。

**难点四：Neo4j 驱动返回结构导致前端图谱展示失败（503）。** 图谱数据构建成功后前端一直报 "图谱服务不可用: 'dict' object has no attribute 'labels'"。排查发现 neo4j driver 的 `record.data()` 会把查询结果中的节点转成普通 dict 且不保留 labels 信息，而取数代码仍按 Node 对象访问 `.labels` 属性，必然抛 AttributeError。解决方案：重写图谱查询，用 Cypher 的 `labels()` 与 `coalesce()` 函数在查询层显式返回节点标签与名称，取数侧只处理标量字段，彻底消除类型假设。修复后接口正常返回图谱 JSON（实测单文档 22 节点 / 17 关系）。

**难点五：SQLAlchemy 2.0 兼容性与日志干扰。** 项目使用的 SQLAlchemy 2.0 中 `SELECT 1` 等原生语句需显式 `text()` 包裹，否则抛 NoReferencedTable/UnsupportedCompilation 类错误；另外开发环境开启 SQLAlchemy echo 日志会在高并发下刷屏并阻塞请求处理。解决方案：统一用 `text()` 包裹原生 SQL、将 echo 关闭并将启动日志重定向到文件。

**难点六：JWT 的登出与改密安全性。** 无状态 JWT 天然无法主动作废。解决方案：为每个 token 签发唯一 jti，登出时把 jti 写入 Redis 黑名单并设置与 token 剩余有效期一致的 TTL；改密时对用户记录做 token\_version 自增，签发新 token 时携带当前版本号，鉴权时校验版本一致性，实现全量旧 token 立即失效。

## 八、面试高频追问准备

**Q1：为什么选三路检索而不是只用向量检索？**

单路检索各有局限：BM25 对同义词、口语化表达召回差；向量检索对精确数字、型号、规范术语易失效；图谱检索能回答关系型问题但依赖实体抽取质量。三路互补并用 RRF 融合，在召回率与精确率之间取得平衡，任一路故障可降级不阻塞。

**Q2：RRF 融合的原理？**

RRF 对每路结果的排名取倒数得分 `1/(K+rank)` 累加，K 取 60。它只依赖排名不依赖绝对分数，规避了三路分数尺度不一致（BM25 得分、向量余弦、图谱评分）无法直接相加的问题。

**Q3：为什么用千问做实体抽取而不是规则或词典？**

工业领域实体（设备型号、故障模式、平台模式）开放性强，规则与词典覆盖有限、维护成本高；大模型零样本抽取泛化能力强，配合 JSON 结构化输出可直接入库。代价是延迟与成本，因此用窗口化合并 + 并发压缩调用次数。

**Q4：图谱构建失败或抽取质量差怎么办？**

流水线有 failed 状态与重试机制，重试前清理残留；抽取结果采用 MERGE 幂等写入，重复处理不产生重复节点；实体名规范化（去空白、统一大小写）降低重复实体概率。业务上可通过提示词约束实体类型清单提升质量。

**Q5：如何保证回答不幻觉？**

检索证据强制进上下文，提示词约束 "仅依据参考资料回答，资料未覆盖则明确说明"；返回 sources 供溯源；热点缓存复用已验证答案。

**Q6：JWT 黑名单和 token\_version 的区别？**

黑名单管单 token 登出（细粒度、即时），token\_version 管用户全量凭证作废（改密场景），两者叠加覆盖登出与改密两种安全需求。
